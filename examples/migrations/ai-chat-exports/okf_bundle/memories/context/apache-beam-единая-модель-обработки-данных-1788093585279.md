# Apache Beam: Единая модель обработки данных

**User:** Расскажи о апаче бим

**Assistant:** ## Что такое Apache Beam?

**Apache Beam** — это фреймворк с открытым исходным кодом и единая модель программирования для создания пайплайнов обработки данных. Его ключевая идея заложена в самом названии: **B** atch + str **EAM** = **BEAM** .

Главная фишка Apache Beam — **абстракция от среды выполнения** . Вы один раз описываете логику трансформации данных, а затем можете запустить этот код на разных распределенных движках без переписывания пайплайна.

## Ключевые концепции

В основе Beam лежит несколько базовых сущностей:

* **Pipeline (Конвейер):** Граф обработки данных от источника до финальной назначения. Управляет всеми этапами выполнения.
* **PCollection (Parallel Collection):** Распределенный набор данных в конвейере.

* *Bounded PCollection* — ограниченный объем (для пакетной обработки / Batch).
* *Unbounded PCollection* — бесконечный поток (для стриминга / Streaming).
* **PTransform (Parallel Transform):** Операция над данными. Принимает `PCollection` , выполняет логику (фильтрацию, маппинг, агрегацию) и возвращает новую `PCollection` .

* Основные примеры: `MapElements` , `Filter` , `ParDo` (аналог Map/FlatMap с контекстом), `GroupByKey` , `Combine` .
* **Pipeline I/O:** Набор готовых коннекторов для чтения и записи данных (Kafka, PostgreSQL, BigQuery, AWS S3, Pub/Sub и т. д.).

## Движки выполнения (Runners)

Вы пишете код с использованием **Beam SDK** , а за распределенные вычисления отвечает выбранный **Runner** :

* **Direct Runner:** Исполняет пайплайн локально на вашей машине. Идеально для отладки и юнит-тестов.
* **Google Cloud Dataflow:** Облачный управляемый сервис от Google (исторически Beam вырос из Google Dataflow SDK).
* **Apache Flink / Apache Spark:** Популярные open-source распределенные движки для On-Premise или облачных кластеров.

## Почему выбирают Apache Beam?

* **Единый API для Batch и Streaming:** Не нужно использовать разные фреймворки для ночных ETL-задач и обработки событий в реальном времени.
* **Гибкость и задел на будущее:** Можно легко сменить инфраструктуру (например, перейти с локального Flink в cloud-native Dataflow), не меняя бизнес-логику пайплайна.
* **Продвинутая работа со временем (Event-Time Processing):** В стриминге Beam мощно справляется с опоздавшими данными (late data) благодаря механизмам:

* **Windowing:** Разбиение потока на окна (Fixed, Sliding, Session).
* **Watermarks:** Отслеживание полноты поступивших данных с учетом задержек сети.
* **Triggers:** Настройка правил, когда именно генерировать результат (например, не дожидаясь закрытия окна).

## Поддерживаемые языки (SDK)

Beam предоставляет официальные SDK для **Python** , **Java** и **Go** . Также поддерживается **Cross-language Transforms** , что позволяет, например, использовать Java-коннекторы прямо из Python-кода.

## Подробный разбор ролей

### 1. Dagster (Оркестратор)

Dagster отвечает за **жизненный цикл и связность** вашей инфраструктуры данных.

* **Концепция Software-Defined Assets (SDA):** Dagster фокусируется не просто на «задачах» (tasks), а на «активах данных» (таблицах, файлах, ML-моделях), которые эти задачи создают.
* **Что делает:**

* Следит за тем, чтобы пайплайн запустился вовремя или по событию.
* Управляет передачей контекста и конфигураций между шагами.
* Логирует метаданные (сколько строк записано, сколько времени заняло, прошла ли проверка качества).
* Предоставляет удобный UI для отслеживания состояния всей системы.

### 2. Apache Beam (Движок обработки)

Beam отвечает за **масштабируемые вычисления** над массовыми данными.

* **Единый API (Batch + Streaming):** Позволяет писать один и тот же код для обработки статичных батчей и бесконечных потоков данных в реальном времени.
* **Что делает:**

* Читает терабайты данных из Kafka/BigQuery/S3.
* Выполняет сложную распределенную трансформацию (фильтрация, скользящие окна/windowing, соединение потоков).
* Распределяет нагрузку по кластеру через Flink, Spark или Dataflow.

## Как они работают вместе?

Dagster и Apache Beam **не исключают, а дополняют друг друга** . На практике Dagster часто используется для оркестрации пайплайнов, внутри которых вызываются задачи на Apache Beam.

В таком сценарии Dagster отвечает за старт задачи Beam, передачу параметров, отслеживание успешности ее завершения и запуск последующих шагов.

## Где Apache Beam ИМЕЕТ смысл в архитектуре

### 1. Batch Inference на огромных объемах (Пакетные предсказания)

В Apache Beam есть встроенный API **`RunInference`** (поддерживает PyTorch, TensorFlow, ONNX, TensorRT и Scikit-learn).

* **Сценарий:** Вам нужно каждую ночь прогнать 100 млн пользователей через ML-модель и записать результаты в базу.
* **Почему Beam:** Он автоматически батчит запросы, эффективнее загружает веса модели в память воркеров кластера и параллелит процесс без риска уронить инфраструктуру по памяти.

### 2. Борьба с Train/Serve Skew (Расхождением признаков)

Главная проблема MLOps — когда признаки (features) для обучения считаются одним способом (SQL-скриптами в DWH), а в продакшене для онлайн-инференса — другим (Python-кодом в сервисе).

* **Почему Beam:** Вы пишете **один пайплайн** , который умеет читать исторические данные из S3/BigQuery для обучения (Batch) и стримить события из Kafka для продакшена (Streaming), гарантируя 100% идентичность логики расчета признаков.

### 3. Стриминговая генерация признаков для Feature Store

* **Сценарий:** Модели нужны агрегации за последние 15 минут (например, «количество транзакций по карте за 15 минут»).
* **Почему Beam:** Благодаря мощному механизму окон (Windowing) и вотермарок (Watermarks), Beam читает поток из Kafka, рассчитывает скользящие агрегации и записывает их в Feature Store (Feast, Redis, Bigtable) с минимальной задержкой.

### 4. Экосистема TFX (TensorFlow Extended)

Если вы строите MLOps-платформу на базе экосистемы Google TFX, то Apache Beam является стандартным подкапотным движком для валидации данных ( `tf.DataValidation` ) и трансформации признаков ( `tf.Transform` ).

## Как Apache Beam работает на слоях Медальона

`[ Источники данных ]
 (Kafka, Pub/Sub, API)
 │
 ▼
 ┌───────────────┐ ┌───────────────┐ ┌───────────────┐
 │ BRONZE LAYER │ ───► │ SILVER LAYER │ ───► │ GOLD LAYER │
 │ (Raw Data) │ Beam │(Cleaned/Enrich) Beam │ (Aggregated) │
 └───────────────┘ └───────────────┘ └───────────────┘`

### 1. Bronze Layer (Сырые данные)

* **Задача слоя:** Принять данные из источников (Kafka, CDC, вебхуки, файлы) и сохранить их в исходном ("сыром") виде с минимальной обработкой.
* **Роль Beam:** Работает как надежный коннектор и инжестор. Beam считывает высоконагруженный поток событий из очереди и записывает его в объектное хранилище (S3, GCS) или табличный формат (Apache Iceberg, Delta Lake).
* **Плюс Beam:** Встроенная обработка сбоев сети и гарантированная доставка *at-least-once* или *exactly-once* .

### 2. Silver Layer (Очищенные и обогащенные данные) — *Главная зона применения Beam*

* **Задача слоя:** Валидация схем, дедупликация, очистка, парсинг (например, JSON/Protobuf) и обогащение данных.
* **Роль Beam:** Это идеальное место для Apache Beam. В Beam удобно реализовывать:

* **Dead Letter Queue (DLQ):** Поврежденные записи не роняют пайплайн, а отправляются в отдельный топик/папку для анализа.
* **Дедупликация:** Механизмы состояния ( *Stateful Processing* ) позволяют эффективно убирать дубликаты в окнах времени.
* **Очистка и маппинг:** Применение строгой бизнес-логики и типов данных с помощью Python/Java/Go SDK.

### 3. Gold Layer (Витрины данных и агрегаты)

* **Задача слоя:** Готовые витрины для BI-инструментов, аналитиков и ML-моделей (агрегаты за день/час, бизнес-метрики).
* **Роль Beam:** Справляется с агрегацией по сложным временным окнам ( *Fixed, Sliding, Session Windows* ) в реальном времени (например, «расчет среднего чека за последние 15 минут с учетом опоздавших транзакций»).

## Резюме

Использовать Apache Beam для медальонной архитектуры **очень даже стоит** , если ваш дата-платформенный стек строится вокруг **обработки событий в реальном времени (Streaming Lakehouse)** , либо если вы работаете в **Google Cloud (Dataflow)** или на кластерах **Apache Flink** .

Если же ваш Lakehouse исключительно пакетный ( *batch-only* ), нацелен на классические SQL-трансформации и строится вокруг Databricks, проще и эффективнее использовать Spark + dbt.
