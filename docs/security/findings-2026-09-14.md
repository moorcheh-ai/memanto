# Security findings — 2026-09-14

Submitted for the Memanto Security Challenge (#1852). All testing was performed
against two throwaway tenant accounts owned by the reporter, on namespaces
containing only synthetic markers; no third-party data was accessed. Cloud-side
behavior was characterized with the official `moorcheh_sdk` (v1.3.7) against
`api.moorcheh.ai`.

## FINDING-05 (Medium-High) — Untrusted text can steer the backend `#key:value` retrieval-filter channel (memory poisoning → context suppression)

**Summary.** The retrieval backends execute `#key:value` tokens found inside the
`query` field as server-side metadata filters — the same syntax `_build_filtered_query`
deliberately uses for trusted app-side filters. Before this PR, free text that the
package does not fully control flowed into that same field:

- `memory_read_service._build_filtered_query` concatenated the caller's `query`
  verbatim next to the trusted filter tokens;
- `daily_analysis_service` built the daily-summary retrieval query and the
  conflict-report digest **from memory contents** (`full_text`) and sent them as
  `query`;
- `generate_answer` forwarded the user query as-is.

Because memory contents are attacker-influenceable (a written memory, an ingested
file, a summarized conversation), a poisoned memory became a dormant payload: when
its text ended the retrieval query, the injected filter decided which documents the
LLM was allowed to see. This PR neutralizes the tokens at those four sinks; the
descriptions below describe the pre-fix (vulnerable) revision.

**Experimentally characterized parser behavior** (test namespace, 7 indexed docs):

| Query sent to `/answer` | LLM context docs |
|---|---|
| plain note text | 7 |
| same text + trailing `#agent:<value-not-present>` (real metadata key) | **0** |
| `... #agent:<value-present-on-one-doc>` | **1** |

The filter applies when the token is the final one of the query and its key matches
an existing document metadata key; unrecognized keys are ignored; any text after the
token disables it; a filter-only query returns a raw 500.

**Impact.** Suppression (or targeted selection) of the context behind daily summaries
and conflict reports: an attacker can hide the memories that contradict their
injected ones, so conflicts are never surfaced and the payload persists — the
"memory as trojan horse" scenario this bounty describes. `/recall` and `/answer`
user queries are the same channel (self-affecting, lower impact).

**Fix (this PR).** `memanto/app/utils/query_safety.py:neutralize_filter_syntax`
defuses `#key:value` tokens in free text at the four sinks where untrusted text
became a backend query, while the trusted filter tokens appended by
`_build_filtered_query` are unaffected. Because the daily-analysis digest
concatenates non-contiguous truncation slices, sanitization is applied to the
**final truncated query** (a `#` and a `key:value` fragment harmless in the source
can reassemble into a live token across slice boundaries). Regression tests in
`tests/test_query_safety.py`, including the end-to-end daily-summary poisoning shape.

**Backend recommendation (out of this repo).** Parse filters only from a structured,
authorized parameter — never from the free-text query field.

## FINDING-02 (Medium, conditional) — `upload-url` signs unsanitized `file_name` (path traversal in S3 object keys)

`POST /v1/namespaces/{ns}/upload-url` accepts `file_name` values containing `../`
and signs them into the object key verbatim; the S3 PUT is accepted (200). S3 keys
are opaque strings, so storage-level escape does not occur, but: (a) object keys
outside the `{tenant}/{ns}/` shape are persisted and listed back by `list-files`;
(b) the extension whitelist validates a *normalized* path while the *original* is
signed (`x.txt/../../../pwn` → 400 quoting `./pwn`); (c) any downstream consumer
that normalizes keys into filesystem paths materializes the traversal.
The Memanto app already basenames filenames before upload (`routes/memory.py`
`upload_file`), so this is a backend hardening item: validate/reject `file_name`
server-side (charset allowlist, no separators, no `..`, cap length) and derive the
key from the validated basename.

## FINDING-03 (Low) — `/answer` leaks raw provider errors; no model allowlist

Invalid `ai_model` (and the `namespace=""` path) returns 500 with the provider's
original `ValidationException` message, fingerprinting the LLM backend. `ai_model`
is forwarded unrestricted. Recommend: server-side model allowlist, generic client
facing errors, and rejecting empty namespaces.

## FINDING-01 (Low) — Internal pipeline timings disclosed on every search response

`/search` responses include a `timings` object (`authorize`, `validate_namespace`,
`prepare_vector`, `fetch_data`, …) exposing the backend architecture and a
fine-grained timing oracle. Recommend stripping it from production responses
(keep in server-side logs).

## FINDING-04 (Informational) — Internal identifiers exposed

`fetch-text-data`'s `next_token` is base64 JSON embedding the internal `userId`
(replay across users is correctly rejected — the binding is validated server-side);
presigned URLs disclose bucket name/region and the tenant UUID key segment.
Recommend an opaque signed cursor and treating the key layout as sensitive.

## Additional notes (package-level, not fixed here)

- `daily_analysis` retrieval loads all session content and every recall path
  over-fetches up to the 100-row cap per namespace; combined with unbounded
  `batch-remember` growth this is a logical-DoS surface worth a limit.
- The agent-conflict client embeds backend response excerpts into error messages;
  `utils/errors.py` includes `original_error` in 500 details — same Low class as
  FINDING-03.

## Negative results (for completeness)

Cross-tenant isolation held on every vector attempted with the two reporter-owned
accounts: namespace listing, document get-by-id, write into a foreign namespace,
similarity search (single and multi-namespace), prefix enumeration, cross-tenant
`next_token` replay, `/answer` against a foreign namespace, and cross-tenant
namespace deletion. Vector uploads validate dimension server-side. The JWT fallback
secret and session auto-renew paths in this repo are correctly hardened.
